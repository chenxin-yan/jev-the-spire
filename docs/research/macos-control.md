# Research: macOS observation and input for an unmodified STS2 run

Research date: 2026-09-18. Scope: [Establish macOS observation and input-control feasibility](https://github.com/chenxin-yan/jev-slay-the-spire-2/issues/4), supporting [Plan a watchable Jev-driven Slay the Spire 2 run on macOS](https://github.com/chenxin-yan/jev-slay-the-spire-2/issues/1). **Evidence:** primary documentation and upstream source inspection, not target-Mac testing. No installation, permission changes, inference calls, or desktop interaction were performed.

## Summary

Apple supplies credible supported primitives for window capture, OCR, and synthetic mouse/keyboard input, but their existence does not establish STS2 compatibility or complete game-state perception ([ScreenCaptureKit](https://developer.apple.com/documentation/screencapturekit/capturing-screen-content-in-macos), [Vision](https://developer.apple.com/documentation/vision/vnrecognizetextrequest), [CGEvent](https://developer.apple.com/documentation/coregraphics/cgevent)). Recommend a gated on-Mac feasibility probe using these native APIs before selecting visual control; keep Jev as sole strategist and treat perception/input as fallible technical services, consistent with [the run brief](https://github.com/chenxin-yan/jev-slay-the-spire-2/issues/1).

## Findings

### 1. Capture is feasible at the platform level; visibility is a separate condition

**Verified documentation.** Apple's sample enumerates displays/apps/windows with `SCShareableContent`, selects a window with `SCContentFilter(desktopIndependentWindow:)`, and receives frames through `SCStream`. The fetched sample requires **macOS 15+ and Xcode 16+**; that is the sample's requirement, not a claim that the entire framework began with macOS 15 ([Apple sample](https://developer.apple.com/documentation/screencapturekit/capturing-screen-content-in-macos)).

Apple documents desktop-independent window capture retaining full content when occluded or off-screen and pausing when minimized. Its WWDC22 baseline explicitly excludes separate child/pop-up windows and describes application-inclusion display filtering as an alternative. Therefore, verify actual tooltip/dialog coverage under the chosen SDK/configuration rather than treating historical defaults as a guarantee for every current configuration ([Apple window behavior](https://developer.apple.com/videos/play/wwdc2022/10155/?time=423), [application filters](https://developer.apple.com/videos/play/wwdc2022/10155/?time=990)).

**Proposed implication.** Begin with game-window-only capture, audio/microphone capture disabled. Check tooltips, dialogs, and overlays against the spectator's actual view. A good captured image cannot establish that the game is unobscured or that a desktop click will reach it; input needs its own visibility/focus gate ([Apple filtering and occlusion](https://developer.apple.com/videos/play/wwdc2022/10155/?time=234)).

### 2. Retina mapping and capture freshness are correctness requirements

**Verified documentation.** Stream dimensions can remain fixed while window content is resized/scaled into the output. Apple supplies `contentRect`, `contentScale`, and `scaleFactor`, distinguishing logical points from backing pixels and showing Retina/non-Retina transitions. Blindly dividing screenshot coordinates by two is not a general conversion ([Apple metadata](https://developer.apple.com/videos/play/wwdc2022/10155/?time=589)).

**Proposed requirements.** Carry frame identity and Mac-local capture time, process/window identity, pixel dimensions, content rectangle, current window bounds, and scale metadata. Explicitly convert crop/image coordinates through window content into desktop coordinates, including origin/orientation conventions. Invalidate mapping after movement, resizing, display/Space changes, or UI-scale changes; validate harmless pointer locations before gameplay ([Apple geometry metadata](https://developer.apple.com/videos/play/wwdc2022/10155/?time=814), [Quartz event locations](https://developer.apple.com/documentation/coregraphics/cgevent)).

Apple's sample rejects invalid buffers and frames without `.complete` status; its metadata includes display time. Apple also warns that holding capture surfaces or processing slowly causes latency/stalls. **Proposed policy:** release buffers promptly, retain the newest usable observation, and revalidate decision-critical state after Jev responds. Wait for relevant UI regions to settle, not for animated backgrounds to become identical; distinguish static content from capture failure using stream health. Never blindly repeat input whose effect is uncertain ([sample validation](https://developer.apple.com/documentation/screencapturekit/capturing-screen-content-in-macos), [queue behavior](https://developer.apple.com/videos/play/wwdc2022/10155/?time=1466)).

### 3. Supported input exists; Accessibility permission is not a semantic game API

**Verified documentation/source.** `CGEvent` exposes mouse, keyboard, and scroll-event creation plus posting into the event stream and process-targeted posting. Hammerspoon's upstream implementation creates keyboard events and posts down/up pairs through Quartz; this is source-level evidence of an existing automation path, not proof that STS2 accepts every synthetic gesture ([Apple CGEvent](https://developer.apple.com/documentation/coregraphics/cgevent), [Hammerspoon implementation](https://raw.githubusercontent.com/Hammerspoon/hammerspoon/master/extensions/eventtap/libeventtap.m)).

Apple explains that visual controls drawn inside another view require explicit accessibility elements to make them discoverable and interactive to accessibility clients. Consequently, **do not assume a rendered game exposes cards, enemies, or buttons through AX**. Inspect the actual tree; a top-level window alone is insufficient. Conversely, absence of semantic AX controls does not by itself rule out pixel observation plus Quartz input—these are different interfaces ([Apple custom-control guidance, archived](https://developer.apple.com/library/archive/documentation/Accessibility/Conceptual/AccessibilityMacOSX/ImplementingAccessibilityforCustomControls.html), [Quartz events](https://developer.apple.com/documentation/coregraphics/cgevent)).

### 4. Human TCC setup must remain explicit and narrowly scoped

**Verified documentation.** Apple's capture sample prompts for Screen Recording permission and instructs restarting the sample afterward. Apple separately requires explicit approval for third-party accessibility access in Privacy & Security settings and advises granting it only to trusted apps ([capture permission](https://developer.apple.com/documentation/screencapturekit/capturing-screen-content-in-macos), [Accessibility permission](https://support.apple.com/guide/mac-help/allow-accessibility-apps-to-access-your-mac-mh43185/mac)).

**Proposed setup:** use an identified GUI helper launched by the human; verify capture and input permissions separately under its actual bundle/executable identity. Recheck after rebuilding/updating it. Determine whether the chosen stop/listening mechanism requires Input Monitoring on the target OS rather than requesting it speculatively. No SIP/TCC weakening, blanket Terminal access, Full Disk Access workaround, or unattended consent approval belongs in this plan ([Apple permission guidance](https://support.apple.com/guide/mac-help/allow-accessibility-apps-to-access-your-mac-mh43185/mac), [ticket constraints](https://github.com/chenxin-yan/jev-slay-the-spire-2/issues/4)).

### 5. OCR versus a vision helper: different failure modes, same provenance requirement

**Verified documentation.** `VNRecognizeTextRequest` is available from macOS 10.15 and finds/recognizes text in images. It offers speed/accuracy selection, minimum text height, supported-language discovery, language correction, custom words, and request revisions. These support a native OCR candidate, not a complete game-state extractor ([Apple Vision](https://developer.apple.com/documentation/vision/vnrecognizetextrequest)).

**Proposed OCR policy:** evaluate accurate recognition on native-resolution text crops; record language, revision, and correction settings. Test small/angled card text, digits, modifiers, and tooltips against human-labeled examples. Preserve raw text and uncertainty instead of silently correcting results from remembered game rules. Text extraction alone does not establish icon meanings, target relationships, or map connectivity; those remain explicit perception-coverage tests ([OCR capabilities](https://developer.apple.com/documentation/vision/vnrecognizetextrequest)).

A separate vision model can describe image content, but its owning documentation explicitly warns about small text, rotation, precise spatial localization, counting, and incorrect descriptions; preprocessing can also resize images. Thus it is an optional transcription/structuring helper, **not a dependable coordinate oracle or second strategist**. No provider/model selection is made here ([OpenAI vision limitations](https://platform.openai.com/docs/guides/images-vision#limitations)).

**Proposed authority/provenance boundary:** retain frame/crop references, capture time, raw transcription, entity bounds, recognizer/model version, and unknown/conflicting fields. The helper may describe visible objects and options; it must not rank cards, recommend targets, choose routes/rewards, or optimize moves. Jev alone decides. Hover inspection may follow Jev requests or fixed read-only enumeration; reacquire geometry after hover-induced layout changes. Treat screen text as observation data, never controller instructions ([strategy ownership](https://github.com/chenxin-yan/jev-slay-the-spire-2/issues/1), [vision limitations](https://platform.openai.com/docs/guides/images-vision#limitations)).

### 6. Minimal stack and operational alternatives—not an architecture decision

| Candidate | Evidence and tradeoff |
|---|---|
| **Native Mac helper** | ScreenCaptureKit + Vision OCR + Quartz input uses supported Apple APIs and avoids an extra automation runtime. Recommendation for the first feasibility probe; still requires application glue and game-specific perception validation ([capture](https://developer.apple.com/documentation/screencapturekit/capturing-screen-content-in-macos), [OCR](https://developer.apple.com/documentation/vision/vnrecognizetextrequest), [input](https://developer.apple.com/documentation/coregraphics/cgevent)). |
| **Existing automation reuse** | Consider Hammerspoon input only if its upstream release is approved/available; inspected source confirms Quartz usage. It does not remove capture/OCR work. Its screenshot backend and current release compatibility were not qualified here; do not assume ScreenCaptureKit equivalence or recommend a local patch ([upstream input source](https://raw.githubusercontent.com/Hammerspoon/hammerspoon/master/extensions/eventtap/libeventtap.m)). |

**Deployment proposals:** orchestration can run locally on the Mac, or Linux can orchestrate an authenticated Mac helper. In either case, capture, input, permission checks, focus checks, and stopping remain local Mac responsibilities. The split option adds disconnect/stale-command handling; it does not require VNC/RDP or a publicly exposed desktop-control endpoint. The research checkout's Linux environment is not target-Mac compatibility evidence ([scope constraints](https://github.com/chenxin-yan/jev-slay-the-spire-2/issues/4), [macOS APIs](https://developer.apple.com/documentation/coregraphics/cgevent)).

**Comparison/recommendation:** visual control preserves an unmodified client but must reconstruct state from fallible observations. A structured bridge should be compared for coverage and stable state/action identifiers by the integration lane, not presumed working from a README. Recommend visual control as the main route only after the coverage/safety gates below pass; otherwise prefer investigating a validated upstream bridge over hiding missing state behind another strategist ([comparison brief](https://github.com/chenxin-yan/jev-slay-the-spire-2/issues/1), [perception limitations](https://platform.openai.com/docs/guides/images-vision#limitations)).

### 7. Stop safety and usage sizing

**Proposed local input gate:** before each bounded operation, require the selected game process/window to be foreground, visible, geometrically calibrated, and consistent with the referenced observation. Pause and clear pending operations on focus loss, minimization/lock, capture/permission failure, unknown state, or remote disconnect. Do not repeatedly steal focus. Revalidate after Jev latency; do not queue long macros or replay uncertain clicks. A focus check cannot retract an already-posted event, so minimize in-flight actions and test that residual boundary ([capture visibility](https://developer.apple.com/videos/play/wwdc2022/10155/?time=423), [event posting](https://developer.apple.com/documentation/coregraphics/cgevent)).

Provide a visible local stop control serviced independently of model/network waits, cancel pending actions, and release any held inputs. A keyboard interception shortcut must not be the only stop path: Hammerspoon's source notes that Secure Input prevents interception, and event taps can be disabled. Require deliberate rearming after disruptive failures ([Hammerspoon event-tap behavior](https://raw.githubusercontent.com/Hammerspoon/hammerspoon/master/extensions/eventtap/libeventtap.m)).

**Illustrative assumptions, not measured demand:** 500 Jev decisions × three observation images gives 1,500 native OCR passes; tooltip sweeps/retries add more. Sending 20% to an optional vision helper gives 300 image inputs. At an assumed 2,000 input/500 output text tokens per Jev turn, estimate 1 million input and 250,000 output tokens before growing history/retries. Instrument actual counts, dimensions, latency, and charges. Vision-image billing depends on model/detail/dimensions, so a dollar estimate awaits the API lane and selected helper; there is no proposed cost ceiling ([image accounting](https://platform.openai.com/docs/guides/images-vision#calculating-costs), [run requirements](https://github.com/chenxin-yan/jev-slay-the-spire-2/issues/1)).

## Gaps and minimum future on-Mac validation

These are **future probes, not performed tests**, under the [ticket's human-setup boundary](https://github.com/chenxin-yan/jev-slay-the-spire-2/issues/4).

| Probe | Observable pass/fail criterion |
|---|---|
| **Inventory/version/CPU** | Record macOS, CPU/native-versus-translated execution, game build/language, window/fullscreen mode, resolution/UI scale, displays, helper identity. Pass only when the human can run the visible game and the chosen APIs/sample support that machine; the fetched Apple sample specifically needs macOS 15/Xcode 16 ([sample](https://developer.apple.com/documentation/screencapturekit/capturing-screen-content-in-macos)). |
| **Permissions and AX** | After human consent, separately demonstrate capture and harmless input; inspect actual AX controls. AX passes as a semantic source only if relevant game elements/text exist—not merely a window ([permission](https://support.apple.com/guide/mac-help/allow-accessibility-apps-to-access-your-mac-mh43185/mac), [AX guidance](https://developer.apple.com/library/archive/documentation/Accessibility/Conceptual/AccessibilityMacOSX/ImplementingAccessibilityforCustomControls.html)). |
| **Harmless capture/input** | Capture menu/tooltip, point at several safe locations, and open/close a harmless menu. Pass when images match the visible current state, pointers remain inside intended targets, and no other-app input or run/save progression occurs ([capture](https://developer.apple.com/documentation/screencapturekit/capturing-screen-content-in-macos), [input](https://developer.apple.com/documentation/coregraphics/cgevent)). |
| **Geometry/overlay changes** | Repeat after intended move/resize/mixed-DPI/fullscreen changes. Pass only with correct recalibration or clean pause; verify tooltip/dialog inclusion ([Apple geometry/filter behavior](https://developer.apple.com/videos/play/wwdc2022/10155/?time=589)). |
| **Visible-state coverage** | Label combat hand/hover text, costs, energy, HP/block, intents/statuses, targets, relics/potions; then menus, map, rewards/skip, shop/removal, rest/upgrade, events, piles, confirmations, and endings as applicable. Pass only when critical fields/options are correct or explicitly unknown; an unknown must block a dependent action ([OCR scope](https://developer.apple.com/documentation/vision/vnrecognizetextrequest), [vision risks](https://platform.openai.com/docs/guides/images-vision#limitations)). |
| **Freshness and stop** | Exercise animations, delayed responses, focus loss, minimization, capture failure, and optional remote disconnect. Pass when changed/stale state blocks input, queues clear, and local stop remains responsive. Measure stop latency and any already-in-flight event; require no subsequent queued events ([queue risks](https://developer.apple.com/videos/play/wwdc2022/10155/?time=1466), [event taps](https://raw.githubusercontent.com/Hammerspoon/hammerspoon/master/extensions/eventtap/libeventtap.m)). |
| **Small pilot** | After approval, cover combat plus reward/map/noncombat transitions. Pass with Jev-originated decisions and evidence-linked observations, no hidden tactical helper choices; one pilot does not establish full-run reliability ([run brief](https://github.com/chenxin-yan/jev-slay-the-spire-2/issues/1)). |

**Unanswered:** actual Mac/game configuration, AX coverage, accepted synthetic gestures, OCR accuracy, tooltip window behavior, intended-session consent persistence, stop-listener permission requirements, and game performance under capture/OCR load. None is established by the general APIs or inspected automation source ([Apple capture](https://developer.apple.com/documentation/screencapturekit/capturing-screen-content-in-macos), [CGEvent](https://developer.apple.com/documentation/coregraphics/cgevent), [Vision](https://developer.apple.com/documentation/vision/vnrecognizetextrequest)).

**Retrieval limitation:** the initial run encountered `Firecrawl Fetch API error (429): Rate limit exceeded` and a coordination timeout. Following release, seven sequential primary fetches succeeded, resolving the draft's OCR/input/TCC/AX documentation gaps. No substitute HTTP execution mechanism was used. Sources are live pages/mutable upstream source, not historical snapshots or proof of target-Mac behavior.
