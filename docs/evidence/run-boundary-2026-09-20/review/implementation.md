# Run-boundary implementation: persistent `combat_loop_cancelled` + `unverified_grid_subclass:NDeckEnchantSelectScreen`

Repo `main`, HEAD `4bbd8c2`, working tree modified (uncommitted, source only under `mod/STS2MCP/`). No commits, install, UI, game requests, save/settings edits or provider calls. Scratch evidence: `/tmp/jev-run-boundary-2026-09-20/native/` (all command logs/exits, IL dumps, `final.diff`, baseline DLL copy).

## Root causes

**Issue 1 (verified).** `McpMod.Contract.cs` held one `static readonly BridgeSession` for the process. `BridgeSession.Fail` is sticky (`Failure` set, `_pending=true`, never refreshed again), and nothing observed the native new-run lifecycle, so a retained old combat-loop cancellation (`CombatExitOperation.Check` → `combat_loop_cancelled` inside `HoldUntil` → `Refresh` → `Fail`) poisoned every later run in the same game process. Fingerprint/revision changes (`Observe`) never clear failures by design, so a fresh Neow could not get past the old failure.

**Issue 2 (verified).** `AddGridActions` (`McpMod.LegalActions.cs`) bound exactly four `NCardGridSelectionScreen` subclasses by `GetType()` equality; `NDeckEnchantSelectScreen` (Read the Back / Read a Random Passage enchant events) was refused as `unverified_grid_subclass`. In addition `BuildCardSelectState` only knew Upgrade/generic preview container names, so an enchant preview would have looked like "no preview" (grid clicks exposed while the native preview container blocks input). Latest log `run-2026-09-20T20-35-24-506Z.jsonl`: halt after `choose_event_option:0` at `d780453c…:130`; selection not adopted.

## Minimal design

Issue 1 — run-scoped epoch (approved by supervisor, including the InitializeNewRun boundary):
- `BridgeProtocol.FreshRunEpoch(currentManager, runPresent, numReloads) => currentManager && runPresent && numReloads == 0`.
- `BridgeSession`: `Run { get; init; }` (epoch's RunState), sticky `_cleanupFailed` set when `Release()` throws, `Retire()` = `Dispose()` once unless cleanup previously failed; returns false when the epoch must be kept.
- `McpMod.NewRunPostfix(RunManager __instance)` — Harmony **postfix, observation only**, installed in the existing pinned `InstallSelectionOwnershipHooks` list (fails the whole hook install if the ABI changes). Reads `RunManager.Instance` identity, `DebugOnlyGetState()`, `_numReloads`, then `BeginRunEpoch(run)`.
- `BeginRunEpoch(run)`: no-op for the same `RunState` (duplicate boundary keeps its failure); `previous.Retire()` releases owners/subscriptions exactly once (combat exit, event/treasure operations, button/executor/CombatEnded handlers via the existing `OnRelease` chain); on cleanup failure the failed epoch stays (`mutation_cleanup_failed`, sticky); otherwise closes stale `_eventEntry`, drops `_restEntry`, and installs `new BridgeSession { Run = run }` (new GUID epoch ⇒ every old `state_version` is 409). `_bridgeSession` lost `readonly`; nothing else reads it in a closure.
- Dispatch methods (`DispatchOwnedTask`, `DispatchPotion`, `DispatchMap`, `DispatchEndTurn`, `DispatchEventOption`, `DispatchTreasurePick`) capture `var session = _bridgeSession;` so late native callbacks keep their own session identity (enforced by an IL test over every compiler-generated closure).
- Not done deliberately: no reset on CLI reconnect, Observe/fingerprint change, map/room transition, Continue/saved run (`numReloads >= 1`, and those setups never call `InitializeNewRun`), no broad reset endpoint, no blanket nulling of `_combatExit`/`_eventOperation`/`_treasureOperation` (their own release callbacks already do it; a callback failure keeps the failed epoch instead).

Issue 2 — enchant selector via the shared grid contract:
- `AddGridActions`: exact `typeof(NDeckEnchantSelectScreen)` added to the five inspected types (unknown subclasses still `unverified_grid_subclass:*`); new shared completeness guard (approved option (a)): base `_cards` (the exact list passed to `ShowScreen`) must equal the allocated `NGridCardHolder` card models by reference and multiplicity (`BridgeProtocol.SameCards`); empty grid with non-empty candidates ⇒ `waiting` (the proven `InitGrid(Task)` await window); any other mismatch ⇒ halt `grid_candidates_incomplete`.
- `BuildCardSelectState`: `screen_type: "enchant"`, `card_select.enchantment {title, description, amount}` from the exact native labels/field (`description` is validated required rules text ⇒ empty text halts), and `%EnchantSinglePreviewContainer`/`%EnchantMultiPreviewContainer` join preview detection so `preview_showing`, preview cards, `can_confirm`/`can_cancel` and the `confirm_selection`/`cancel_selection` labels follow the native preview state. Existing Smith empty/cancel behaviour, custom null-Room reward identity guards and all prior tests untouched.
- README: documents the process-scoped session/new-run boundary and the large-deck `grid_candidates_incomplete` limitation.

## Limits and risks (truthful)
- Offline reflection/IL certifies metadata and compiled wiring only; Harmony patch application, Godot main-thread ordering of the `StartNewSingleplayerRun` continuation, and live UI behaviour are not proven here. No live run performed.
- The boundary fires at `InitializeNewRun`, before `GenerateRooms`/`Launch`; observations during that setup window behave exactly as the process-start epoch always did (unchanged exposure).
- New behaviour for all grid lanes: decks larger than the allocated window now halt `grid_candidates_incomplete` instead of silently pruning (approved; documented). Empty-grid `waiting` relies on the proven `InitGrid(Task)` await; if a grid never allocates, the CLI's own wait timeout is the backstop.
- A cleanup failure during retirement (or earlier in that session) intentionally leaves the bridge failed for the rest of the game process (`mutation_cleanup_failed`); recovery is a game restart. `_combatExit`/`_eventOperation`/`_treasureOperation` are not force-nulled; their release callbacks run in `Retire()`.
- `Formatting.cs` markdown (multiplayer-only path) does not render the new `enchantment` block; the singleplayer CLI consumes JSON and has no `screen_type` dependency (grep of `src/`).
- The halted enchant selection from `run-2026-09-20T20-35-24-506Z.jsonl` was not adopted or resumed.

## Both issues fixed?
Yes at the source/offline-verification level for the authoritative mod: (1) a verified new run opens an independent epoch, old failures/versions/callbacks cannot poison it, same-run/saved-run/reconnect failures stay latched; (2) `NDeckEnchantSelectScreen` is handled through the shared grid contract with preview, rules text and full-candidate proof. Live confirmation (install + fresh run + an enchant event) remains a separately approved step.
